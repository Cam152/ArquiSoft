### 2.3 Descripción

AGORA es un sistema de votación electrónica. Los administradores crean elecciones, registran sus
candidatos y las abren o cierran. Los votantes inician sesión con su documento y su clave, eligen un
candidato en una elección abierta y emiten un único voto. Después, cualquier persona puede consultar el
conteo y el porcentaje que obtuvo cada candidato.

El sistema se construye alrededor de dos garantías:

- **Una persona, un voto.** El votante se marca como "ya votó" antes de guardar el voto, en una sola
  actualización atómica, de modo que un segundo intento se rechaza.
- **Voto anónimo.** Quién votó y qué se votó viven en bases de datos distintas, cada una de un servicio
  diferente. El voto guardado solo tiene la elección, el candidato y una fecha redondeada a la hora, y
  nada que identifique al votante.

### 3.1 Estructura de componentes y conectores (C&C)

#### 3.1.1 Vista C&C

![Vista C&C de AGORA](AGORA_CC.png)

#### 3.1.2 Estilos arquitectónicos usados

| Estilo | Cómo lo usa AGORA |
|---|---|
| **Basado en servicios (distribuido)** | La lógica se divide en tres servicios de grano grueso, uno por dominio (votantes, votos y elecciones). Cada uno se despliega por separado, está escrito en un lenguaje distinto y no comparte código con los demás. |
| **SOFEA (Service-Oriented Front-End Architecture)** | El navegador descarga la aplicación web una sola vez y desde ahí consume los servicios directamente. Ningún servicio genera páginas. |
| **Tres capas (three-tier)** | Los componentes se organizan en los niveles de presentación (`-fr`), lógica (`-lo`) y datos (`-db`). Un componente solo se comunica con el nivel inferior o con un par del nivel de lógica. |
| **Base de datos por servicio** | Cada servicio es el único dueño de su base de datos. Los demás componentes solo llegan a esos datos a través de la API del dueño. |
| **Cliente-servidor** | Toda interacción es una petición y respuesta síncrona sobre HTTP (REST o GraphQL) o sobre un protocolo de base de datos. |

#### 3.1.3 Elementos arquitectónicos y relaciones

Cada componente lleva el mismo nombre que su contenedor de Docker (`container_name` en `docker-compose.yml`),
con la forma `agr-<nombre>-<nivel>`: `-fr` es presentación, `-lo` es lógica y `-db` es datos. Así el nombre de la
vista es el que muestra `docker ps`.

**Componentes**

| # | Componente | Nivel | Tecnología | Responsabilidad |
|---|---|---|---|---|
| 1 | `agr-frontend-fr` | Presentación | TypeScript, React, Vite (servido por nginx) | Aplicación web que corre en el navegador. Muestra las elecciones con su estado y sus candidatos y es el punto de entrada de los votantes. |
| 2 | `agr-voter-lo` | Lógica | Java, Spring Boot | Autentica a los votantes (documento y clave) y emite un JWT. Lleva el control de quién ya votó con `mark-voted` y `unmark-voted`. |
| 3 | `agr-vote-lo` | Lógica | Go (`net/http`) | Recibe el voto, lo valida con los otros dos servicios, lo guarda de forma anónima y calcula los resultados de una elección. |
| 4 | `agr-election-lo` | Lógica | Python, FastAPI, Strawberry | Administra las elecciones, sus candidatos y su ciclo de vida (borrador, activa, cerrada). Las expone por REST y GraphQL. |
| 5 | `agr-voters-db` | Datos | PostgreSQL | Base de datos relacional con los votantes, el hash de su clave y la marca "ya votó". |
| 6 | `agr-votes-db` | Datos | MongoDB | Base de datos NoSQL (documental) con los votos anónimos y los eventos de auditoría. |
| 7 | `agr-elections-db` | Datos | PostgreSQL | Base de datos relacional con las elecciones y sus candidatos. |

**Conectores**

En la vista, cada conector HTTP (REST o GraphQL) se dibuja con la notación de interfaz de UML: el **círculo** está
pegado al puerto del componente que **ofrece** la API (el servidor) y el **semicírculo** que lo abraza sale del
puerto del componente que la **consume** (el cliente). Los conectores a base de datos se dibujan con una flecha
punteada que apunta a la base. En la tabla, "Desde" es el cliente y "Hacia" es el servidor.

| Conector | Desde → Hacia | Puertos | Propósito |
|---|---|---|---|
| REST (HTTP, JSON) | `agr-frontend-fr` → `agr-voter-lo` | p1 → p2 | Inicio de sesión del votante (`POST /auth/login`), que devuelve el JWT. |
| REST (HTTP, JSON) | `agr-frontend-fr` → `agr-vote-lo` | p3 → p4 | Emitir un voto (`POST /votes`) y consultar los resultados (`GET /results/{election_id}`). |
| GraphQL (HTTP) | `agr-frontend-fr` → `agr-election-lo` | p5 → p6 | Consultar las elecciones con sus candidatos anidados en una sola petición. |
| REST (HTTP, JSON) | `agr-vote-lo` → `agr-election-lo` | p15 → p16 | Comprobar que la elección existe, está abierta y contiene al candidato elegido (`GET /elections/{id}`). |
| REST (HTTP, JSON) | `agr-vote-lo` → `agr-voter-lo` | p13 → p14 | Marcar al votante como "ya votó" (`POST /voters/mark-voted`) y deshacerlo si el voto no se puede guardar (`POST /voters/unmark-voted`). |
| Conexión a base de datos (JDBC, protocolo de PostgreSQL) | `agr-voter-lo` → `agr-voters-db` | p7 → p8 | Leer y actualizar votantes. |
| Conexión a base de datos (protocolo de MongoDB) | `agr-vote-lo` → `agr-votes-db` | p9 → p10 | Insertar votos y eventos de auditoría, y agregar los resultados. |
| Conexión a base de datos (protocolo de PostgreSQL) | `agr-election-lo` → `agr-elections-db` | p11 → p12 | Leer y escribir elecciones y candidatos. |

**Relaciones**

- El front-end es el único componente que usa una persona. Se conecta con los tres componentes de
  lógica y nunca con una base de datos.
- Cada componente de lógica se conecta con exactamente un componente de datos, y cada componente de
  datos está conectado con exactamente un componente de lógica.
- `agr-vote-lo` coordina el flujo de votación. Primero le pregunta a `agr-election-lo` si el voto es
  válido, luego le pide a `agr-voter-lo` que marque al votante y por último guarda el voto en
  `agr-votes-db`. PostgreSQL y MongoDB no comparten transacción, así que si el último paso falla,
  compensa desmarcando al votante.
- `agr-voter-lo` y `agr-election-lo` no se llaman entre sí, y ninguno de los dos llama a `agr-vote-lo`.
- El sistema usa dos tipos de conector HTTP (REST y GraphQL), dos tipos de base de datos (relacional y
  NoSQL) y tres lenguajes de propósito general en el nivel de lógica (Java, Go y Python), además de
  TypeScript en el nivel de presentación.

## 4. Prototipo

Requisitos: Git y Docker con Docker Compose (con el motor corriendo), y los puertos `3000`, `8000`, `8001`, `8002`
y `5432` del equipo libres. Si el `5432` está ocupado por un PostgreSQL local, crear un archivo `.env` con
`VOTERS_DB_PORT=5433`.

```bash
git clone https://github.com/Cam152/ArquiSoft.git
cd ArquiSoft
docker compose up --build
```

La primera ejecución descarga las imágenes base y construye los cuatro servicios, así que puede tardar varios
minutos. El sistema está listo cuando `docker ps` muestra los siete contenedores `agr-*` corriendo.

| Contenedor | Dirección |
|---|---|
| `agr-frontend-fr` | http://localhost:3000 |
| `agr-election-lo` | http://localhost:8000/docs (REST) y http://localhost:8000/graphql (GraphQL) |
| `agr-voter-lo` | http://localhost:8001/health |
| `agr-vote-lo` | http://localhost:8002/health y http://localhost:8002/results/1 (resultados de la elección 1) |

Para usar el sistema se abre http://localhost:3000 y se ingresa con uno de los votantes de ejemplo: documentos
`1000000001` a `1000000005`, todos con la clave `voter123`. Cada votante puede votar una sola vez. Para administrar
elecciones (crearlas, abrirlas o cerrarlas) se usa http://localhost:8000/docs, escribiendo la llave `dev-admin-key` en el
campo `x-api-key` de cada operación.
